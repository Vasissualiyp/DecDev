# AGENTS.md

## What this repo is

DecDev: a catalog of reusable, declaratively-specified game-development
*capabilities* (movement, camera, combat, inventory, etc.), inspired by but
never containing the proprietary source/assets of the games that inspired
them. Think "npm registry, but for game-mechanic specs" — not a game engine.

Current state: **pre-implementation**. Only specs and docs exist so far; no
`components/`, `site/`, or `cli/` directories yet. If you're an agent picking
up work here, your first job is almost certainly something from
[`specs/06-build-plan.md`](specs/06-build-plan.md) Tier 1.

## Read before doing anything architectural

- [`docs/architecture.md`](docs/architecture.md) is the design-of-record —
  the *why* behind every decision below. If a task seems to require a
  judgment call not covered by the specs, check here before improvising.
- [`specs/`](specs/) is the mechanical *how* — schemas, file layout, exact
  CLI commands, CI steps, task-by-task build plan. Follow it; don't
  redesign in place. If a spec is wrong or missing something, update the
  spec file first, then write code against the corrected spec — don't let
  code and spec drift apart.
- [`prompt.md`](prompt.md) is the original brief these were derived from.
  Read it for context on intent, not as a literal task list — `docs/` and
  `specs/` already resolved its open questions into decisions.

## Hard constraints (do not relitigate these without updating docs/architecture.md first)

- No hosted code execution, no automated game-decompilation pipeline, no
  runtime component composition in the MVP or alpha. The platform stores
  and serves *metadata* (specs) and links out to externally-hosted
  implementations — it does not host or run implementation code.
- No proprietary game source, ROMs, extracted assets, textures, models, or
  audio — ever, in any form, including as "reference material" in a commit.
  `reference_games` fields are named inspirations only.
- Infra budget is effectively $0: static hosting, no managed database,
  until a feature genuinely can't work without one (see
  `specs/06-build-plan.md` Tier 3, task 12 — the first one that needs a DB).
- Every component spec under `/components` must validate against
  `/schema/component.schema.json` (once it exists). A PR that adds an
  invalid spec should fail CI, not get hand-waved.
- **Every `url`/`demo_url` in a component spec must be a real link you
  have personally verified resolves — never invent one, including by
  copying the placeholder pattern from `specs/01-capability-spec-format.md`'s
  example.** This happened once already (an agent filled an entire seed
  set with fabricated `github.com/...` links that all 404'd) — it is now
  also a mechanical CI link-check (`specs/05-validation-ci.md`), but the
  rule exists independent of the check: don't wait for CI to catch what
  you already know you didn't verify.

## Stack

Two languages, split by what the code *is*, not by convenience — full
rationale in [`specs/00-overview.md`](specs/00-overview.md):

- **CLI and infra: Rust.** The shared schema-validation library
  (`crates/core`), the CLI (`cli/`), and any future backend (REST API,
  MCP server) are Rust, compiled to native binaries, one Cargo workspace.
  No Node/TypeScript here, ever — the CLI is meant to be installed like
  `ripgrep` or `fd`, not like an npm package.
  - **If an agent proposes Node/TypeScript/Python for the CLI, the shared
    validation library, or any backend service, stop and reread
    `specs/00-overview.md` — that's the one constraint this repo will
    not relitigate casually.**
- **Website: TypeScript/JavaScript, deliberately.** `site/` (Astro,
  Pagefind) is the one explicit exception — ordinary web tooling for an
  ordinary static site. It's a separate npm project, not part of the
  Cargo workspace, and it never parses YAML or re-implements validation:
  it only ever reads `site/src/data/components.json`, generated by the
  Rust CLI's `decdev export` command. See `specs/02-repo-layout.md` and
  `specs/04-cli.md`.

Don't introduce a database or a backend framework ahead of where the
build plan calls for them (`specs/06-build-plan.md` Tier 3).

## Testing

Code is extensively tested, not spot-checked. Concrete requirements are in
[`specs/07-testing.md`](specs/07-testing.md) — read it before writing any
code in `crates/core`, `cli/`, `site/`, or the alpha-tier API/MCP server.
Short version: `cargo test` (+ `assert_cmd` for the CLI) on the Rust side,
a lightweight JS test runner for `site/`. `crates/core` gets one test per
required schema field and per non-schema rule (e.g. the
`proprietary_analysis` → `legal_review` gate), every CLI command gets a
test per flag/branch (including its error paths, e.g. `show` on an
unknown slug, and `export`'s all-or-nothing behavior), and `site/` gets
unit tests on its data loading plus a build-and-inspect-the-output
integration test per page — `site/` does NOT test validation, since by
design it never sees invalid data (see `specs/00-overview.md`). A task
from [`specs/06-build-plan.md`](specs/06-build-plan.md) is not done when
it merely runs correctly by hand — it's done when its listed test cases
exist and pass in CI. If a change to validation logic, a CLI flag, or an
error condition doesn't have a corresponding case in `specs/07-testing.md`,
add one there in the same PR rather than leaving the list stale.

## Conventions

- One component = one YAML file at `/components/<slug>.yaml`, `<slug>`
  kebab-case and matching the filename exactly.
- Validation logic lives in one shared crate (`crates/core`, package
  `decdev-core`), used by `cli/` and CI — never duplicate schema-loading
  or validation code elsewhere, and never re-implement it in `site/`
  (which only reads the already-validated `components.json` export).
- `site/` is an independent npm project, not a Cargo workspace member and
  not an npm workspace either — its only link to the Rust side is the
  generated `components.json` file (see `specs/02-repo-layout.md`).
- No multi-paragraph comments or docstrings in code. A one-line comment is
  fine for a genuinely non-obvious invariant; everything else should be
  legible from naming.

## Commands

`cargo`/`rustc` are not on the default `PATH` on this machine — prefix every
cargo invocation with `nix develop --command` (the repo's `flake.nix`
provides a working Rust toolchain). The package name for the CLI crate is
`decdev` (not `cli` — that's just the directory name), so use `-p decdev`.

- `nix develop --command cargo build --workspace`
- `nix develop --command cargo test --workspace`
- `nix develop --command cargo clippy --workspace --all-targets -- -D warnings`
- `nix develop --command cargo fmt` (and `--check` to verify without changing)
- `nix develop --command cargo run -p decdev -- <list|search|show|validate|export>`
  — all five subcommands are implemented (`specs/06-build-plan.md` Tiers 1–2
  tasks 1-5 are done); see `specs/04-cli.md` for exact flags per command.

`site/` doesn't exist yet (Tier 2, `specs/06-build-plan.md` task 6) — once
it does, add its `npm run build --prefix site` command here too.
